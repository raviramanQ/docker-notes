01 Why Docker? The Problem It Solves ▼

Imagine you're building a Node.js app with Node v16 and MongoDB 4.2. Works perfectly on your machine. A new team member joins — they install dependencies manually, get version mismatches, and things break. This is the classic "works on my machine" problem.

😤 Without Docker
  • Each dev installs deps manually
  • Version mismatches cause errors
  • Env differences break builds
  • "It works on my machine!" syndrome
  • Onboarding takes hours/days
✅ With Docker
  • App + all deps packed in one unit
  • Same container runs anywhere
  • Onboarding = just pull & run
  • Multiple versions side by side
  • No conflicts between projects
💡 Docker solves the environment consistency problem by bundling the application with all its dependencies into a single portable unit called a container.
02 Core Concepts: Image vs Container ▼
🖼 Docker Image
  • Executable blueprint/template
  • Contains app + all its dependencies
  • Static — does not run by itself
  • Like a Class in OOP
  • Stored on Docker Hub (registry)
  • Smaller in size (no runtime memory)
📦 Docker Container
  • A running instance of an image
  • Has its own isolated file system
  • Dynamic — actively consumes resources
  • Like an Object in OOP
  • One image → multiple containers
  • Larger (occupies RAM when running)

Analogy: Image is like a class, Container is like an object created from that class. You can create many objects (containers) from one class (image).

🔑 Key Properties of Containers
  • Portability — run on any OS without changes
  • Isolation — completely separate from host OS and other containers
  • Lightweight — minimal overhead, fast to start/stop
  • Layered — images are built in layers (efficient storage & sharing)
03 Installation & Setup ▼

Download Docker Desktop from docker.com — available for Mac, Windows, Linux. Docker Desktop includes the Docker engine, CLI, and a GUI.

Verify Installation
docker
# If Docker is installed, shows list of available commands
docker --version
# Shows installed Docker version
💡 Docker Desktop GUI shows Containers (left panel) and Images. You can manage everything from GUI or CLI — CLI is preferred in practice.
04 Essential Docker Commands ▼
Images
docker pull <image-name>
# Download image from Docker Hub
docker pull mysql:8.0
# Pull specific version using tag
docker images
# List all local images
docker rmi <image-name>
# Remove an image (must remove containers first)
Containers — Create & Run
docker run <image-name>
# Create + start container from image
docker run -d <image-name>
# Run in detached (background) mode
docker run -it ubuntu /bin/bash
# Run interactively (enter container shell)
docker run --name mydb -d mysql
# Assign custom name to container
docker run -e ENV_VAR=value <image>
# Pass environment variables
Containers — Manage
docker ps
# List RUNNING containers
docker ps -a
# List ALL containers (running + stopped)
docker start <container-name/id>
# Restart a stopped container
docker stop <container-name/id>
# Stop a running container
docker rm <container-name/id>
# Delete a container permanently
⚠️ To delete an image, you must first remove all containers using that image. You cannot delete an image that's in use, even by a stopped container.

🔢 Image Layers

Docker images are made of layers. Each version of an image shares common base layers. When pulling a new version, only the different layers are downloaded — not the whole image again. This saves storage.

05 Port Binding (Host ↔ Container) ▼

Each container has its own internal ports. To access a service inside a container from your browser/app, you must map (bind) a host port to the container's port.

Port Binding Diagram
Your Browser (localhost:8080)
→
Host Port 8080
→
Container Port 3306
→
MySQL inside container
Port Binding Syntax: -p host_port:container_port
docker run -d -p 8080:3306 mysql
# Map host:8080 → container:3306
docker run -d -p 27017:27017 mongo
# MongoDB: same port on both sides
docker run -d -p 8081:8081 mongo-express
# Mongo Express UI
⚠️ Port conflict: Two containers CANNOT be mapped to the same HOST port. If port 8080 is taken, use 8081, 8082 etc. Container ports can be the same since they're isolated.
06 Debugging Containers ▼
Logs & Shell Access
docker logs <container-id>
# See all logs from a container
docker logs -f <container-id>
# Follow live logs (like tail -f)
docker exec -it <container-name> /bin/bash
# Enter interactive shell inside RUNNING container
exit
# Exit shell — container keeps running!
💡 docker exec -it is used to enter a running container. Exiting does NOT stop the container — it just disconnects your shell session.
07 Docker vs Virtual Machines ▼
Feature Docker Container Virtual Machine
VirtualizesApplication layer onlyOS kernel + application
SizeMBs — very lightweightGBs — heavy
Startup timeSecondsMinutes
OS compatibilityLimited (shares host kernel)Any OS, fully independent
Resource usageLow — shares host resourcesHigh — dedicated resources
IsolationProcess-levelFull OS-level
💡 Docker's main disadvantage: since it virtualizes only the application layer (not the kernel), containers need to be compatible with the host OS kernel. VMs don't have this limitation since they virtualize the full OS.
08 Docker Networking ▼

Docker networking controls how containers talk to each other and to the outside world. For containers to communicate (e.g., Node.js app talking to MongoDB), they need to be on the same network.

3 Default Network Drivers
  • Bridge (default) — containers on same host can talk to each other; most common use case
  • Host — container shares the host machine's network; no separate IP for container
  • None — fully isolated; no networking at all
Default Bridge Network

Containers can communicate but need extra config (IP addresses). Less convenient.

Custom Bridge Network

Containers talk using container names directly. Much easier! This is what you use in real apps.

Network Commands
docker network ls
# List all networks
docker network create mongo-network
# Create a custom network
docker run -d --network mongo-network --name mongo mongo
# Run container inside a specific network
Demo: MongoDB + Mongo Express on same network

MongoDB container + Mongo Express container placed in mongo-network. Mongo Express connects to MongoDB using the container name mongo instead of an IP or localhost. This is why custom networks are so powerful.

Full setup commands
docker network create mongo-network
docker run -d \
-p 27017:27017 --name mongo \
--network mongo-network \
-e MONGO_INITDB_ROOT_USERNAME=admin \
-e MONGO_INITDB_ROOT_PASSWORD=kty \
mongo
docker run -d \
-p 8081:8081 --name mongo-express \
--network mongo-network \
-e ME_CONFIG_MONGODB_ADMINUSERNAME=admin \
-e ME_CONFIG_MONGODB_ADMINPASSWORD=kty \
-e ME_CONFIG_MONGODB_SERVER=mongo \
mongo-express
09 Dockerfile — Dockerizing Your App ▼

A Dockerfile is a text file with instructions to build your own Docker image. In production, tools like Jenkins automatically build Docker images from your code using Dockerfiles.

Key Dockerfile Instructions
InstructionPurposeExample
FROMBase image to build uponFROM node:16
WORKDIRSet working directory inside containerWORKDIR /app
COPYCopy files from host into imageCOPY . /app
RUNExecute command at build timeRUN npm install
CMDCommand to run when container starts (only 1)CMD ["node", "server.js"]
EXPOSEDocument which port the container usesEXPOSE 5050
ENVSet environment variablesENV NODE_ENV=production

Example Dockerfile for Node.js app:

# Dockerfile (capital D, no extension!)
FROM node:16

# Set environment variables
ENV MONGO_USERNAME=admin
ENV MONGO_PASSWORD=kty

# Create working directory
WORKDIR /test-app

# Copy all files from host into container
COPY . /test-app

# Install node modules at build time
RUN npm install

# Expose container port
EXPOSE 5050

# Start command (only ONE allowed)
CMD ["node", "test-app/server.js"]
Build & Run Your Image
docker build -t test-app:1.0 .
# Build image from Dockerfile in current dir (-t = tag)
docker images
# Verify image was created
docker run -d -p 5050:5050 test-app:1.0
# Run your custom image
docker run -it test-app:1.0 bash
# Enter container interactively to explore
💡 RUN executes at build time (when creating the image). CMD executes at run time (when starting the container). Only one CMD allowed — the last one wins.
10 Docker Compose — Multi-Container Management ▼

Running 2–3 containers with long docker run commands is messy. Docker Compose lets you define all containers in a single .yaml file and manage them with simple commands.

docker-compose up

Creates and starts all containers defined in the yaml file. Add -d for detached mode.

docker-compose down

Stops and removes all containers AND the created network. Permanent removal.

docker-compose.yaml example (MongoDB + Mongo Express):

version: '3'

services:
  mongodb:
    image: mongo
    ports:
      - "27017:27017"
    environment:
      - MONGO_INITDB_ROOT_USERNAME=admin
      - MONGO_INITDB_ROOT_PASSWORD=kty

  mongo-express:
    image: mongo-express
    ports:
      - "8081:8081"
    environment:
      - ME_CONFIG_MONGODB_ADMINUSERNAME=admin
      - ME_CONFIG_MONGODB_ADMINPASSWORD=kty
      - ME_CONFIG_MONGODB_SERVER=mongodb
💡 Docker Compose automatically creates a network for all services defined in the file — no need to manually create one like we did earlier. Services can reference each other by service name.
Compose Commands
docker-compose -f docker-compose.yaml up -d
# Start all services in background
docker-compose -f docker-compose.yaml down
# Stop and remove all containers + network
⚠️ Before running docker-compose up, stop and remove any manually created containers using the same ports to avoid conflicts.
11 Volumes — Data Persistence ▼

Problem: When a container stops or is deleted, all data inside it is lost. Databases especially need persistent storage across restarts.

Solution: Docker Volumes — mount a host directory into the container so data is saved on your machine.

3 Types of Volumes
  • Named Volume — has a name, Docker manages location; best for production
  • Anonymous Volume — no name, temporary storage; can become orphaned
  • Bind Mount — you specify exact host path; most control, used in dev
Volume Commands
docker volume ls
# List all volumes
docker volume create my_volume
# Create a named volume
docker run -v /host/path:/container/path ubuntu
# Bind mount: link host folder to container folder
docker run -v my_volume:/data ubuntu
# Named volume: attach to container
docker volume prune
# Delete all unused/orphaned volumes

Volumes in Docker Compose (for MongoDB persistence):

services:
  mongodb:
    image: mongo
    volumes:
      - /Users/you/Desktop/data:/data/db
      # host path : container path
💡 When you restart containers with volumes attached, the data reappears — databases, collections, everything. This is how real apps maintain data across deployments.
12 Docker Hub — Sharing Images ▼

Docker Hub is the public registry where images are stored. You can push your own images so teammates can pull them directly — no need to share source code separately.

Push Your Image to Docker Hub
docker build -t your-username/test-app:1.0 .
# Build with repo name matching Docker Hub repo
docker logout
# (Optional) logout of any existing session
docker login
# Login with Docker Hub credentials
docker push your-username/test-app:1.0
# Push all layers to Docker Hub
docker pull your-username/test-app:1.0
# Pull your own image back / others can pull it
Production Workflow (CI/CD)
Dev pushes code
→
Jenkins (CI/CD)
→
docker build
→
docker push to Hub
→
Server pulls & deploys

Common docker run flags to remember
  • -d — detached (background) mode
  • -it — interactive terminal mode
  • -p H:C — port binding (host:container)
  • --name — assign name to container
  • -e KEY=VAL — set environment variable
  • --network — specify network
  • -v host:container — bind mount volume
📌 Important Things to Remember
  • Image → Container is like Class → Object
  • Must remove containers before removing their image
  • Two containers can't share the same HOST port
  • Only ONE CMD in a Dockerfile (last one wins)
  • Data is lost on container deletion unless volumes are used
  • Docker Compose auto-creates a network for all services
  • Custom bridge networks let containers communicate by name
  • exec -it only works on RUNNING containers
